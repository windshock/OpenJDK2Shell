## 3. Episode 프로토콜 (드라이버 고정값)

웜업 20,000회(유효 4형태, 예외 입력 없음) → fill 100개 + 중립 1개(각 `byte[6291400]`, 6리전) →
attempt k=1..K(K=12): drop `f(70+k)` → 동시 마킹 사이클 완료 대기(최대 90s, pump 32MB) →
**C2 게이트**(PrintCompilation상 tier-4 `decode0` live가 아니면 유효 입력 2,000회 재웜업, 최대 10라운드; 실패 시 그 attempt는 INVALID `c2-gate-failed`) →
**feature 스냅샷** → trigger(`A×4·2097136 + tail`) → post 사이클 대기(최대 60s) →
liveness(`/api/login` 401, 캐시 미접촉) → 헤더 관측(`/api/diag`).
종료: JVM 사망 또는 K 도달. control arm은 trigger 결과 배열을 즉시 DELETE해 live heap을 맞춘다.

**순서:** arm 순서는 블록 무작위화한다 (10 블록 × 4 arm, 블록마다 순열을 섞음, seed=20261123). 노드·시간대 효과가 한 arm에 몰리지 않게 하기 위함이다.

## 4. 결과 정의

| 필드 | 정의 |
|---|---|
| `process_crash` (1차 라벨) | trigger 이후 다음 trigger 전까지 JVM이 사망 (liveness 실패, 또는 관측 중 사망) |
| episode 크래시 | episode 내 attempt 중 `process_crash=1`이 하나라도 있음 |
| `live_object_corruption` | `/api/diag` 길이 ≠ 6291400인 캐시 배열 존재 → OBSERVED, 전부 일치 → NOT_OBSERVED, 관측 불가 → UNKNOWN |
| `crash_during_observation` | liveness 통과 후 `/api/diag` 호출 중 사망 (관측 교란, P0-7) |
| `intrinsic_reached` | PrintCompilation상 tier-4 `Base64$Decoder::decode0`가 trigger 이전에 존재하고 not-entrant가 아님 → `INFERRED_TRUE` (직접 관측 아님) |
| `logical_oob_observed`, `disclosure_observed` | 이 랩에서는 측정하지 않음 (`NOT_MEASURED`) |

**INVALID:** JVM 미기동, fill 실패, trigger 전 사망(`died-before-trigger`), 설정 불일치(effective `UseBASE64Intrinsics`가 arm 정의와 다름). INVALID 행은 분석에서 제외하되 원본은 보존하고 제외 건수를 보고한다.

## 5. 실험 A — 인과 판정

- N = **episode 10 / arm** (INVALID episode는 같은 arm으로 보충, 최대 3회)
- 1차 검정: episode 크래시 비율. A1 vs A2, A1 vs A3, A1 vs A4 각각 **Fisher exact (단측, A1 > 비교군)**, Holm 보정, α=0.05
- **causal supported:** 세 비교 모두 유의 + A2·A3·A4 크래시율 ≤ 10%
- **not supported:** A1 크래시율이 A4와 유의차 없음 (포화·부하가 원인일 가능성)
- **inconclusive:** 그 외 (예: A1 재현율이 낮아 검정력 부족)
- 2차(보고용, 판정 불변): arm별 `live_object_corruption=OBSERVED` episode 비율, SURVIVED episode 중 OBSERVED 건수

## 6. 실험 B — 예측

- 데이터: 실험 A의 **A1 arm VALID attempt** (malicious, intrinsic ON — 다른 arm은 크래시가 정의상 드묾)
- 라벨: attempt 단위 `process_crash`
- feature (trigger 직전, 드라이버 `gc_features`): `f_cycles_total`, `f_secs_since_last_cycle_end`, `f_humongous_alloc_gcs`, `f_heap_occupancy_after_last_pause`, `f_secs_since_drop`, `f_cycle_rate_60s`, 그리고 `attempt_id`, `shape`
- baseline H0: 로지스틱(`f_heap_occupancy_after_last_pause` 단일)
- 모델 H1: 로지스틱(위 feature 전부, L2 C=1.0, 표준화)
- 1차 지표: **Brier score**, **leave-one-episode-out** 교차검증 (같은 episode의 attempt가 학습·검증에 동시에 들어가지 않음)
- 판정: H1의 Brier가 H0보다 **0.05 이상 낮으면** H1 채택 근거. 미만이면 H0/H2 검토. 양성(크래시) attempt가 **8건 미만**이면 INCONCLUSIVE (검정력 부족)
- 탐색적(1차 결론에 영향 없음): 라벨을 `live_object_corruption=OBSERVED`로 바꾼 동일 분석, UNKNOWN은 제외하고 제외율 보고

### D-1 (2026-11-23, 데이터 0건 시점) — 순차 단일 노드 → 노드별 병렬 lane

- **원래:** §1 "전 arm 동일 노드(dev02), 순차 실행"
- **변경:** 노드당 파드 1개(lane), 블록 단위로 노드 배정 `block b → lane (b-1) mod L` (`research/schedules/make_main.py dev02 dev03 dev04 dev05 dev06`). 블록 내 arm 순서는 등록된 무작위 순열 그대로
- **이유:** 순차 실행 예상 소요 5~9h. 담당자가 워커 dev03~06(8 vCPU·8 GB)을 추가해 병렬화 요청
- **편향 통제:** 블록마다 4 arm이 모두 들어 있으므로 노드 효과는 arm 간에 균형을 이룬다. 각 행에 `lane`(노드)·`cpu_flags`를 기록한다. 분석은 등록된 Fisher 검정을 그대로 쓰고, 노드별 arm 크래시율 표를 보조로 보고한다. **AVX-512 VBMI+BW가 없는 노드의 episode는 INVALID**(설정 불일치) 처리한다
- **영향받은 데이터:** `main-b01-A2` 1회가 attempt 진행 중 중단됨(병렬 전환 작업). 원자료는 `ep_aborted/`, `attempts_all.pre-D1.jsonl`에 격리했고 분석에서 제외한다. 같은 epid는 처음부터 다시 수행한다
- **파드 자원:** 새 lane은 app request 3 CPU / 2.5 GiB (limit 3 CPU / 3 GiB). JVM 설정은 동일하다. dev02 lane은 기존 파드(request 3 CPU / 3 GiB)를 유지한다. CPU limit이 같으므로 GC 스레드 에르고노믹스가 같다
- **D-1 보충 (같은 날):** dev03~06은 VM 부팅 후 쿠버네티스 미가입(CSR·부트스트랩 토큰 0건)이라, 블록 2·7을 **dev01** lane에 배정했다 (AMD EPYC-Genoa, avx512 vbmi/bw/vl, bmi2 확인). dev01에는 다른 팀 워크로드(`n2r-test`)가 함께 돈다. 이 경우도 블록 단위로 배정되므로 arm 간 균형은 유지되며, 노드별 보조표로 보고한다. 11/20 레거시 `spring-lab` 파드는 원자료를 `research/data/legacy-spring-lab-2026-11-20/`에 보관한 뒤 정리했다 (사전등록 데이터 아님)
